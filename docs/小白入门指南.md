# DocFlow 小白入门指南

这篇文档不是给“已经懂这个项目的人”写的，而是给“刚打开仓库、基本不知道自己在看什么”的人写的。

如果你现在的感受是：

- 文件很多，不知道先看哪个
- 前端、后端、OCR、发票识别这些词都混在一起
- 看见 `app.py`、`docflow_core.py`、`invoice_db.py` 也不知道谁先谁后
- 担心项目大部分是 AI 生成的，自己根本接不住

那就按这篇文档来，不要跳读。

---

## 1. 先用一句话理解这个项目

这个项目本质上是一个“文档处理网站”。

用户把文件上传上来，系统会做下面几件事里的一个或多个：

1. 读取文档内容
2. 如果是图片或扫描件，就做 OCR
3. 把结果整理成文本、表格、JSON、Markdown 或 CSV
4. 如果像发票，就额外抽取发票字段
5. 把发票结果保存到 SQLite 数据库
6. 用样本集批量测试效果，生成报告

所以你可以把它理解成：

`一个前端页面 + 一个 Flask 后端 + 一套文档解析/OCR逻辑 + 一套发票抽取逻辑 + 一套测试报告脚本`

## 2. 你现在最需要先知道的事

先别把它想得太复杂。这个仓库不是下面这些东西：

- 不是“训练深度学习模型的项目”
- 不是“纯算法论文代码”
- 不是“复杂微服务系统”
- 不是“只有脚本、没有实际可用界面”的实验仓库

它更像一个已经能跑的工程型项目，重点在：

- 多格式文档处理
- OCR 回退
- 发票结构化抽取
- 样本驱动测试
- 演示型部署

换句话说，这个项目的难点主要不是数学，而是“链路多、模块多、入口多”。

## 3. 你应该先建立的全局地图

先把仓库分成 7 块看：

| 模块 | 你可以怎么理解 |
| --- | --- |
| `frontend/` | 网页界面，用户能看到的东西 |
| `app.py` | 后端总入口，负责接请求、调核心逻辑、回结果 |

| `invoice_extractor.py` | 从文本里提取发票字段 |
| `invoice_db.py` | 把发票结果存进 SQLite |

如果你只记一句话：

`网页在 frontend，后端在 app.py，文档处理在 docflow_core.py，发票逻辑在 invoice_extractor.py 和 invoice_db.py，测试在 scripts/`

## 4. 仓库里最重要的文件，先认识一下

### 4.1 `frontend/doc_tool.html`

这是整个项目的前端页面。

你打开网页后看到的上传区、选项区、结果区、批量测试区、依赖检查区、发票历史区，基本都在这里。

你不用一开始就读懂全部 CSS 和 JS，只需要先知道它负责：

- 选文件
- 调后端接口
- 轮询异步任务状态
- 展示处理结果
- 发起批量测试
- 查看依赖状态
- 查看发票历史记录

对小白来说，前端最重要的价值不是“研究界面”，而是帮你看清楚系统到底提供了哪些功能。

### 4.2 `app.py`

这是后端主入口，也是你最值得先读的 Python 文件。

它的角色不是“做全部工作”，而是“调度中心”。

你可以把它理解成柜台：

- 前端把文件送过来
- `app.py` 判断该走哪条处理链路
- 普通文档交给 `DocFlowProcessor`
- 图片交给 `process_image_ocr(...)`
- 如果开启发票识别，再补发票抽取
- 如果识别出发票，再写入数据库
- 最后把 JSON 结果返回给前端

### 4.3 `docflow_core.py`

这是文档处理主引擎。

它里面最重要的类是 `DocFlowProcessor`。这个类干的事很明确：

1. 根据扩展名找解析器
2. 解析文件
3. 提取关键词和摘要
4. 如果需要，抽取发票字段
5. 按指定格式输出结果

它下面挂了几个解析器：

- `PDFParser`
- `WordParser`
- `ExcelParser`
- `PPTXParser`
- `TextParser`

所以这个文件是“处理规则中心”。

### 4.4 `invoice_extractor.py`

这个文件不是 OCR 引擎，也不是数据库层。

它干的是另一件事：

`已经有一段文本了，怎么判断它是不是发票，并从里面提取发票代码、号码、日期、金额、购销方等字段？`

它主要靠规则、正则和启发式逻辑工作，不是训练模型。

### 4.5 `invoice_db.py`

这个文件专门负责持久化发票记录。

它会把识别结果保存到：

`data/invoices.db`

你只要先知道它负责：

- 建表
- 保存记录
- 分页查询
- 查单条详情
- 删除记录
- 导出 CSV

### 4.6 `docflow_support.py`

这个文件更像“运行环境辅助模块”。

它主要处理：

- 依赖检查
- OCR / LibreOffice / Tesseract 环境探测
- 错误分类
- 结果补充信息
- 安装建议

如果你看到前端里有“依赖检查”，它背后主要就是这个文件在干活。

### 4.7 `scripts/`

这是“验证系统效果”的工具箱。

里面不是业务主链路，而是测试和辅助脚本，比如：

- `run_batch_tests.py`
- `run_evaluation_set.py`
- `run_invoice_evaluation.py`
- `debug_doc.py`

如果你后面要写论文、答辩、做演示，这个目录很重要。

## 5. 这个项目的真实工作流程是什么

这是你最该看懂的一部分。

### 5.1 用户上传普通文档时

主链路大致是：

1. 前端页面选择文件
2. 前端把文件发到 `POST /process/start`
3. `app.py` 先把文件保存到临时目录
4. `app.py` 创建后台线程处理任务
5. 后端根据文件类型决定调用谁
6. 普通文档进入 `DocFlowProcessor.process(...)`
7. `DocFlowProcessor` 根据扩展名选择解析器
8. 解析器提取文本、表格、元数据
9. 后续补关键词、摘要、发票字段
10. 格式化输出结果
11. 前端通过 `GET /process/<job_id>` 轮询拿结果

你可以把它想象成：

`网页发请求 -> app.py 接单 -> docflow_core.py 干活 -> app.py 回结果 -> 前端展示`

### 5.2 用户上传图片时

图片不是走普通解析器那条路，而是单独走 OCR 链路：

1. 前端上传图片
2. `app.py` 识别出扩展名属于图片
3. 调用 `process_image_ocr(...)`
4. 按配置顺序尝试 OCR 引擎
5. 当前环境通常优先用 `RapidOCR`
6. 常见轻量环境下通常会继续尝试 `Tesseract`
7. 如果额外安装了其他引擎，也可能继续尝试 `EasyOCR` 或 `PaddleOCR`
8. 识别出文字后，再按需要做发票抽取
9. 最终结果返回前端

所以：

- 图片处理的重点在 `app.py`
- 文档解析的重点在 `docflow_core.py`

### 5.3 发票识别什么时候发生

发票识别不是单独的上传入口，而是“处理后的附加能力”。

也就是说：

- 先得到文本
- 再从文本里提字段

所以发票识别依赖前面的解析/OCR 结果质量。

如果 OCR 文本很差，发票字段就会跟着差。

### 5.4 发票保存什么时候发生

不是所有文件都会写数据库。

只有在下面条件满足时才会保存：

1. 你开启了发票提取
2. 当前处理结果是成功的
3. 系统在发票抽取结果里判断 `is_invoice = true`

保存位置是：

`data/invoices.db`

## 7. 作为小白，你应该按什么顺序读代码

下面这个顺序比“从头把所有文件都打开”有效得多。

### 第 1 步：先打开网页，知道系统长什么样

先看：

- `frontend/doc_tool.html`

这一步不要细读，目标只是回答两个问题：

1. 这个系统提供哪些功能按钮和面板？
2. 用户大概会怎么操作它？

### 第 2 步：读 `app.py`，建立总流程感

这一步的目标不是吃透所有函数，而是弄清：

- 请求从哪里进来
- 文件保存到哪里
- 普通文档和图片分别怎么处理
- 结果最后怎么返回前端

只要你把 `POST /process/start`、`POST /process`、`process_image_ocr(...)` 看懂，理解就已经前进一大步。

### 第 3 步：读 `DocFlowProcessor.process(...)`

这是核心中的核心。

你要看懂：

- 它怎么找解析器
- 解析完后还会补什么
- 输出格式是怎么决定的

只要这一步看懂，整个“文档处理”主链路就成型了。

### 第 4 步：再看具体解析器

建议顺序：

1. `TextParser`
2. `WordParser`
3. `ExcelParser`
4. `PPTXParser`
5. `PDFParser`

原因很简单：

- 文本解析器最容易看懂
- Office 解析器中等复杂
- PDF 解析器最复杂，里面混了文本层、OCR、模式切换、页面策略

所以不要一上来就硬啃 `PDFParser`。

### 第 5 步：看发票模块

当你已经理解“文本是怎么来的”之后，再看：

- `invoice_extractor.py`
- `invoice_db.py`

这时你会更容易理解：

- 为什么先 OCR，再抽发票字段
- 为什么数据库里存的是结构化结果，不是原始图片

### 第 6 步：最后看测试脚本

先看：

- `scripts/run_batch_tests.py`
- `scripts/run_evaluation_set.py`
- `scripts/run_invoice_evaluation.py`

这一步的目标不是记参数，而是明白：

- 这个项目不是用 `pytest` 为主
- 它更偏“样本集 + 评测清单 + 报告生成”

## 8. 这个项目不是怎么测试的，而是“怎么评测的”

这点你一定要分清。

很多 Python 项目会有：

- `tests/`
- `pytest`
- `unittest`

这个项目当前更偏数据驱动评测，而不是传统单元测试。

### 8.1 通用样本批测

脚本：

- `scripts/run_batch_tests.py`

样本目录：

- `sample_data/test_documents`
- `sample_data/test_documents_edge_cases`

它做的事是：

- 逐个跑样本文件
- 统计成功/失败
- 判断是否符合预期
- 汇总错误类别
- 生成 `report.md`、`results.json`、`results.csv`、`summary.html`

### 8.2 评价集

脚本：

- `scripts/run_evaluation_set.py`

配置文件：

- `sample_data/evaluation_set/sample_manifest.json`

这类评测更接近“人工规则校验”，比如：

- 某文件应该成功还是失败
- 至少要提取多少字符
- 必须包含哪些关键词
- 不应该包含哪些关键词

### 8.3 发票专项评测

脚本：

- `scripts/run_invoice_evaluation.py`

清单：

- `发票样本/invoice_test_manifest.csv`
- `发票样本/invoice_excel_manifest.csv`

它不是简单看“有没有识别出点文字”，而是会区分：

- 是不是识别成发票
- 某个字段有没有提出来
- 提出来的字段对不对

这也是为什么发票模块更像“规则抽取系统”，不是单纯 OCR。

## 9. 小白第一次上手，建议你真的去做这 5 件事

不要只读文档。你需要通过非常小的动作，把仓库和实际行为连起来。

### 9.1 先把服务跑起来

最直接的方式是：

```powershell
python app.py
```

默认本地访问：

```text
http://127.0.0.1:5000
```

如果环境缺依赖，不要慌，先记住这是“运行环境问题”，不是“你没看懂业务”。

### 9.2 先上传一个最简单的文本文件

建议先传：

- `sample_data/test_documents/sample.txt`

你应该观察：

- 前端怎么显示处理中
- 返回结果里有哪些字段
- 结果里的 `text`、`metadata`、`statistics` 大概长什么样

### 9.3 再传一个图片文件

建议传：

- `sample_data/test_documents/sample.png`

你应该观察：

- 这次是不是走了 OCR
- 返回里有没有 `engine`、`ocr_engine_order`
- 发票字段有没有出现

### 9.4 再传一个 PDF

建议先传：

- `sample_data/test_documents/sample_text.pdf`

然后再传：

- `sample_data/test_documents/sample_scan.pdf`

你应该观察：

- 文本型 PDF 和扫描型 PDF 的处理差异
- `fast / balanced / accurate` 模式可能影响什么

### 9.5 最后看一次发票记录

如果你开启了发票抽取并识别出了发票，去看：

- 前端发票历史区
- 或接口 `/invoices`

你就会知道数据库不是抽象概念，而是真的落了数据。

## 10. 你可能会遇到的几个理解误区

### 10.1 误区一：`app.py` 就是全部业务

不是。

`app.py` 更像调度中心，真正的文档解析主要在 `docflow_core.py`。

### 10.2 误区二：OCR 就等于发票识别

不是。

OCR 只是“先把图里的字拿出来”，发票识别是“再从文本里抽字段”。

### 10.3 误区三：支持 `.doc` 就一定完整支持旧版 Office

不是。

当前项目对 `.doc`、`.xls` 有兼容尝试，但真正完整支持旧版二进制格式通常还依赖 LibreOffice 之类的外部工具。

### 10.4 误区四：有测试脚本就说明一定是标准单元测试工程

不是。

这个仓库当前更接近“样本评测型工程”，而不是“单元测试覆盖完整的工程”。

### 10.5 误区五：AI 生成的代码就一定完全不能读

也不是。

这种项目最容易让人害怕的地方，不是代码一定错，而是：

- 文件多
- 功能多
- 命名有时不统一
- 某些模块职责交叉

你的策略不应该是“全读”，而应该是“只抓主链路”。

## 14. 对你现在最实用的建议

你现在最不需要做的事是：

- 一次打开十几个文件
- 一开始就研究所有正则
- 一上来就改 PDF 解析器
- 试图一天内完全吃透整个仓库

你现在最需要做的事是：

1. 先把系统跑起来
2. 用样本文件实际点几次
3. 顺着一次上传请求去跟代码
4. 先弄懂主链路，再弄懂细节

只要这样做，你就会逐渐从“这个仓库我完全看不懂”，变成“这个项目的主干我已经抓住了”。
