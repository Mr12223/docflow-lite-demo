# 项目架构说明（重构后）

本文档基于当前仓库的最新结构重新整理，目标是回答两个问题：

1. 现在这个项目到底是怎么组织的。
2. 如果要继续读代码，应该先看哪一层、每层负责什么。

和旧版本相比，最大的变化是：`app.py` 已经不再承载大部分业务逻辑，后端代码已经明显拆成了 `docflow/` 包内的共享层、路由层、服务层。

---

## 1. 一句话概括现在的架构

当前项目可以理解成 5 层：

1. **入口层**：`app.py`
2. **共享基础层**：`docflow/paths.py`、`docflow/settings.py`、`docflow/runtime.py`
3. **Web 应用层**：`docflow/webapp/core.py`、`docflow/webapp/routes/`
4. **业务服务层**：`docflow/webapp/services/`
5. **文档解析核心层**：`docflow_core.py`、`invoice_extractor.py`、`invoice_db.py`

也就是说，现在的真实结构已经从“单文件大而全”变成了“薄入口 + 分层模块”。

---

## 2. 当前目录职责

### 2.1 根目录核心文件

| 路径 | 作用 |
| --- | --- |
| `app.py` | Flask 启动入口，当前非常薄，主要是从 `docflow.webapp` 重新导出 `app`、`main`、`process_image_ocr` 等对象。 |
| `docflow_core.py` | 文档解析核心，负责 PDF / Word / Excel / PPT / 文本等文件的识别、解析、关键词提取、摘要、格式化输出。 |
| `docflow_support.py` | 依赖检查、错误信息整理、OCR 环境准备、结果增强等辅助工具。 |
| `invoice_extractor.py` | 发票字段抽取规则，负责从 OCR 文本或文档文本中提取发票代码、号码、金额、税号等结构化字段。 |
| `invoice_db.py` | 发票记录的 SQLite 持久化层，负责保存、查询、删除、导出。 |

### 2.2 `docflow/` 包

`docflow/` 现在是后端的基础设施目录，负责把原来分散的“公共能力”集中起来。

| 路径 | 作用 |
| --- | --- |
| `docflow/paths.py` | 统一定义项目路径，例如 `frontend/`、`reports/`、`uploads_temp/`、`data/`、`invoices.db`。 |
| `docflow/settings.py` | 统一处理环境变量、布尔开关、整数配置、PDF 模式标准化。 |
| `docflow/runtime.py` | 统一处理日志、线程限制、Windows 控制台 UTF-8 兼容。 |

### 2.3 `docflow/webapp/`

这是 Flask Web 应用真正所在的位置。

| 路径 | 作用 |
| --- | --- |
| `docflow/webapp/core.py` | 创建 Flask `app`、启用 CORS、初始化日志、准备运行目录、创建 `invoice_db` 单例。 |
| `docflow/webapp/__init__.py` | 导出 `app`，并在导入时注册所有路由，提供 `main()` 用于本地启动。 |
| `docflow/webapp/responses.py` | 统一错误响应等简单响应工具。 |
| `docflow/webapp/routes/` | 只负责接请求、做参数整理、调用服务层、返回 JSON。 |
| `docflow/webapp/services/` | 只负责业务执行，不直接暴露 HTTP 接口。 |

### 2.4 其他目录

| 路径 | 作用 |
| --- | --- |
| `frontend/` | 前端页面，当前入口页仍然是 `doc_tool.html`。 |
| `scripts/` | 批测、评测、样本生成、论文材料生成等脚本。 |
| `sample_data/` | 样本测试数据。 |
| `reports/` | 批测报告输出目录。 |
| `uploads_temp/` | Web 上传文件的临时目录，以及图片 OCR 缓存目录。 |
| `data/` | 持久化数据目录，例如 `invoices.db`。 |

## 3. 现在的启动链路

### 3.1 Web 服务启动

当前启动链路是：

`app.py`
-> `docflow.webapp`
-> `docflow/webapp/core.py`
-> 创建 Flask 应用与共享对象
-> `docflow/webapp/routes/__init__.py`
-> 注册各路由模块

也就是说：

- `app.py` 现在只是一个**兼容入口**。
- 真正的 Flask 应用初始化发生在 `docflow/webapp/core.py`。
- 真正的路由注册发生在 `docflow/webapp/routes/__init__.py`。

### 3.2 命令行与脚本启动

脚本层一般不直接依赖旧式 `app.py` 里的大逻辑，而是：

- 通过 `app.py` 复用图片 OCR 接口
- 或直接调用 `docflow_core.DocFlowProcessor`

例如：

- `scripts/run_batch_tests.py` 会复用 `DocFlowProcessor`
- 图片样本则直接走 `process_image_ocr`

这说明项目已经逐渐形成了“Web 层”和“脚本层”共享底层能力的结构。

---

## 4. Web 层已经如何拆分

这是这次重构最重要的地方。

### 4.1 `core.py`：共享初始化层

`docflow/webapp/core.py` 负责：

- 初始化运行环境
- 限制原生数值库线程数
- 处理 Windows UTF-8 输出
- 创建运行期目录
- 初始化日志
- 创建 Flask `app`
- 启用 CORS
- 初始化 `invoice_db`

这意味着：所有路由和服务都可以复用同一个 `app`、`logger`、`invoice_db`，不需要各自重复初始化。

### 4.2 `routes/`：只处理 HTTP

当前路由已经按功能拆开：

| 路由模块 | 主要职责 |
| --- | --- |
| `routes/common.py` | 首页、报告文件访问、系统依赖检查与安装、`/debug-doc` 调试接口。 |
| `routes/process.py` | 单文件处理接口，包括同步处理和异步任务处理。 |
| `routes/batch.py` | 批量测试任务的启动、轮询、取消。 |
| `routes/invoice.py` | 发票记录的列表、详情、删除、清空、导出。 |

这里最关键的改进是：**路由只管请求，不再把复杂 OCR、批测、持久化逻辑堆在一起。**

### 4.3 `services/`：只处理业务

当前服务层也已经按职责拆开：

| 服务模块 | 主要职责 |
| --- | --- |
| `services/process_jobs.py` | 单文件异步任务状态管理、取消、结果补充、发票记录保存。 |
| `services/batch_jobs.py` | 批量测试任务管理、子进程启动、日志收集、报告整理。 |
| `services/ocr.py` | 图片 OCR 门面层，负责组织多 OCR 引擎、挑选最佳结果、合并发票字段。 |
| `services/ocr_engines.py` | OCR 引擎适配层，负责 RapidOCR / PaddleOCR / Tesseract / EasyOCR 的调用、预处理、缓存、回退顺序。 |
| `services/invoice_merge.py` | 发票 OCR 结果增强层，负责跨引擎评分、税号修复、字段融合。 |

可以把它理解成：

- `routes/` 决定“接口怎么进”
- `services/` 决定“任务怎么做”
- `docflow_core.py` 决定“文档本身怎么解析”

## 5. 真实业务链路是怎么走的

### 5.1 普通文档处理链路

用户上传一个非图片文件后，典型流程是：

1. `routes/process.py` 接收上传文件并保存到 `uploads_temp/`
2. 如果是异步任务，则把任务信息写入 `PROCESS_JOBS`
3. `services/process_jobs.py` 调用 `DocFlowProcessor.process()`
4. `docflow_core.py` 根据文件后缀选择解析器
5. 各解析器完成文本提取、表格提取、摘要、关键词等处理
6. 服务层补充标准化结果
7. 如果启用了发票提取，则额外抽取发票字段并尝试保存到数据库
8. 最终返回 JSON 给前端

这个链路中：

- Web 层只负责任务调度
- 真正的“文档理解”集中在 `docflow_core.py`

### 5.2 图片 OCR / 发票识别链路

如果上传的是图片，链路会变成：

1. `routes/process.py` 识别为图片扩展名
2. 调用 `services/ocr.py` 的 `process_image_ocr()`
3. `ocr.py` 根据 `ocr_engines.py` 里的 OCR 顺序依次尝试引擎
4. 当前默认顺序是：`rapidocr -> tesseract`
5. 每个候选结果都会交给 `invoice_merge.py` 做发票评分
6. 选出最优 OCR 结果
7. 对税号等关键字段做跨引擎修复与合并
8. 生成统一返回结构
9. 如果启用了发票抽取，则保存到 `invoice_db`

这说明当前图片场景已经不是“单 OCR 引擎直出”，而是：

- 多引擎候选
- 结果打分
- 发票字段补强
- 最终融合输出

这部分是整个仓库目前最复杂、也最“工程化”的一块。

### 5.3 批量测试链路

批量测试现在也已经独立成一条清晰链路：

1. `routes/batch.py` 接收批测请求
2. `services/batch_jobs.py` 创建任务状态
3. 后台线程启动 `scripts/run_batch_tests.py`
4. 脚本遍历 `sample_data/` 下的测试集
5. 对每个样本调用 `DocFlowProcessor` 或 `process_image_ocr`
6. 汇总结果并输出到 `reports/batch_test_xxx/`
7. 生成 `summary.html`、`report.md`、`results.json`、`results.csv`
8. 前端通过轮询接口查看进度和报告链接

也就是说，批测并不是写在 Flask 路由里的，而是：

- Flask 负责任务控制
- 脚本负责实际执行
- `reports/` 负责承接结果产物

## 6. 当前各模块之间的边界

为了避免再次回到“所有逻辑都塞进一个文件”的状态，现在最好把边界理解清楚。

### 6.1 应该放在 `routes/` 的内容

- URL 路由
- 请求参数获取
- 上传文件接收
- 返回 `jsonify(...)`
- 调用服务层

不应该放在这里的内容：

- OCR 规则
- SQLite 读写细节
- 批测子进程控制细节
- 发票字段合并算法

### 6.2 应该放在 `services/` 的内容

- 异步任务管理
- 任务取消逻辑
- OCR 调度
- 发票识别融合
- 批测结果整理

不应该放在这里的内容：

- Flask 请求对象直接处理
- 页面文件响应
- 路由定义

### 6.3 应该放在 `docflow_core.py` 的内容

- 文件类型识别
- 解析器选择
- PDF / Word / Excel / PPT / 文本解析
- 关键词提取
- 摘要提取
- 输出格式化

### 6.4 应该放在 `invoice_extractor.py` / `invoice_db.py` 的内容

- 发票字段规则
- 发票数据库结构
- 发票记录 CRUD

## 8. 这次重构后，代码可读性提升在哪里

这次结构调整的价值是实打实的，不只是“目录变多了”。

### 8.1 `app.py` 终于变薄了

以前如果 `app.py` 既负责路由、又负责 OCR、又负责批测、又负责数据库，那阅读入口会非常混乱。

现在：

- `app.py` 只保留启动与兼容导出
- 真正逻辑被放到更明确的位置

这让“从哪里读起”变得清晰很多。

### 8.2 Web 层有了明显分层

当前已经形成：

- `core`：初始化
- `routes`：接口
- `services`：业务

这正是中小型 Flask 项目比较合理的结构。

### 8.3 OCR 逻辑也开始分模块

现在图片 OCR 不再是一大坨混在一起，而是拆成：

- `ocr.py`：总调度
- `ocr_engines.py`：引擎适配
- `invoice_merge.py`：字段融合

这让你读代码时可以先抓“大流程”，再深入某个引擎或某个发票修复细节。

### 8.4 脚本层和 Web 层的关系更清楚了

批测、评测、样本生成已经放在 `scripts/`，不再和 Web 路由混写。

这意味着这个项目已经不仅是一个“网页工具”，也是一个可以独立跑脚本、做实验、产出报告的毕业设计工程。

---

## 9. 当前仍然比较重的地方

虽然已经重构了一大步，但现在仍有几个“大文件”值得注意。

### 9.1 `docflow_core.py` 仍然是最大核心

这个文件依然承担了很多责任：

- 多种解析器定义
- PDF 混合解析策略
- 文本分析
- 输出格式化
- 主处理器门面

它已经比以前更容易配合外围模块使用，但**内部体量依旧很大**。  
如果后续还要继续重构，它仍然是第一拆分对象。

比较合理的后续方向是：

- `parsers/pdf_parser.py`
- `parsers/word_parser.py`
- `parsers/excel_parser.py`
- `analyzers/text_analyzer.py`
- `formatters/output_formatter.py`

### 9.2 `ocr_engines.py` 和 `invoice_merge.py` 也很重

这两个文件已经是“按功能拆”后的结果，但自身又逐渐长大了。

后续如果继续演进，可以再按主题细拆：

- OCR 缓存
- 图像预处理
- 引擎适配器
- Google Vision 相关逻辑
- 税号修复逻辑
- 候选评分逻辑

### 9.3 任务状态目前仍是内存字典

现在：

- `PROCESS_JOBS`
- `BATCH_TEST_JOBS`

都是进程内内存状态。

这对毕业设计、单机演示完全够用，但如果以后要支持：

- 多进程部署
- 服务重启恢复
- 长时间任务追踪

就需要迁移到 Redis / 数据库 / 消息队列等持久化方案。

## 10. 现在应该怎样理解“测试体系”

当前项目其实已经有 3 类测试/验证方式：

### 10.1 样本批量测试

入口脚本：`scripts/run_batch_tests.py`

特点：

- 面向 `sample_data/` 里的测试集
- 会生成 Markdown / JSON / CSV / HTML 报告
- 适合做功能回归和演示

### 10.2 发票专项评测

相关脚本：

- `scripts/run_invoice_evaluation.py`
- `scripts/generate_invoice_excel_manifest.py`
- `scripts/generate_invoice_image_manifest.py`

特点：

- 更偏向发票识别效果验证
- 用于统计字段抽取正确性、样本覆盖情况

### 10.3 综合评测/论文材料生成

相关脚本：

- `scripts/run_evaluation_set.py`
- `scripts/generate_graduation_materials.py`

特点：

- 更偏向毕业设计汇报、实验材料、结果汇总

因此，这个仓库不是“没有测试”，而是采用了**脚本化评测 + 样本报告**的方式，而不是典型的 `pytest` 单元测试为主。

- 再搞清 OCR 和文档解析主链路
- 最后再看批测和报告体系

## 12. 最终结论

当前仓库已经完成了一个很关键的结构升级：

- `app.py` 从“大杂烩”变成了薄入口
- 共享配置沉淀到 `docflow/`
- Flask 路由拆到了 `routes/`
- 任务与 OCR 逻辑拆到了 `services/`
- 文档解析核心保留在 `docflow_core.py`

所以，**现在这个项目最适合的理解方式不是“一个 Flask 文件”，而是“一个以 `DocFlowProcessor` 为核心、以 `docflow.webapp` 为外壳的分层文档处理系统”。**

如果后面还要继续重构，优先级最高的对象依然是：

1. `docflow_core.py`
2. `ocr_engines.py`
3. `invoice_merge.py`

但就“是否比之前更容易读”这件事来说，答案是明确的：**是，而且已经明显更容易建立整体心智模型。**
