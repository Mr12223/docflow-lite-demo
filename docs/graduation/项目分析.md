# DocFlow 项目分析

## 1. 项目定位

DocFlow 是一个已经可运行的多格式文档处理 Web 工具，不只是论文素材仓库。当前项目围绕一条完整链路展开：

`上传文件 -> 文档解析 / OCR -> 结构化结果 -> 发票抽取 -> 批量评测 / 报告导出`

它主要解决三类问题：

- 多格式文档内容提取：PDF、Word、Excel、PPT、TXT、Markdown、JSON、CSV
- 图片 OCR：支持多引擎回退、云环境下的降采样和缓存
- 发票结构化识别：提取字段、保存记录、导出 CSV

## 2. 当前仓库结构

| 路径 | 作用 |
| --- | --- |
| `frontend/doc_tool.html` | 单页前端，负责上传、任务轮询、PDF 模式实验、批测面板、依赖检查、发票记录展示 |
| `app.py` | Flask 服务入口，提供页面、处理任务、批测任务、依赖接口、报告访问、发票记录接口 |
| `docflow_core.py` | 核心处理器，封装解析器、关键词/摘要生成、PDF 模式切换、统一输出格式 |
| `docflow_support.py` | 依赖检测、安装建议、错误归类、Tesseract/LibreOffice 运行环境辅助 |
| `invoice_extractor.py` | 发票字段提取规则，负责判定是否为发票及抽取代码、号码、日期、金额、购销方等字段 |
| `invoice_db.py` | SQLite 持久化层，保存发票记录并支持列表、详情、删除、CSV 导出 |
| `scripts/` | 批量测试、评测、清单生成脚本 |
| `sample_data/` | 通用样本、边界样本、清单式评测样本 |
| `发票样本/` | 发票公开数据集、自建 Excel 真值集及评测清单 |
| `reports/` | 批测和评测报告输出目录 |
| `data/` | 运行期数据目录，当前主要用于保存 `invoices.db` |

## 3. 系统架构

### 3.1 前端层

前端只有一个页面：`frontend/doc_tool.html`。它不是简单上传页，而是一个集成操作台，当前包括：

- 文件上传与处理历史
- PDF 三种模式选择：`accurate`、`balanced`、`fast`
- PDF 模式实验与推荐结果展示
- 一键批量测试和报告链接展示
- 依赖检查与安装建议
- 发票识别结果页签与历史记录面板

### 3.2 接口层

后端使用 Flask，当前关键接口如下：

| 接口 | 作用 |
| --- | --- |
| `GET /` | 返回前端页面 |
| `GET /reports/<path>` | 访问历史报告文件 |
| `GET /system/dependencies` | 查看依赖状态 |
| `POST /system/dependencies/install` | 尝试安装缺失依赖 |
| `POST /process/start` | 启动异步文档处理任务 |
| `GET /process/<job_id>` | 查询异步处理进度与结果 |
| `POST /process/<job_id>/cancel` | 取消处理任务 |
| `POST /process` | 同步处理单文件 |
| `POST /run-batch-tests` | 启动异步批量测试 |
| `GET /run-batch-tests/<job_id>` | 查询批测状态和报告链接 |
| `POST /run-batch-tests/<job_id>/cancel` | 取消批测任务 |
| `GET /invoices` | 分页查询发票记录 |
| `GET /invoices/<id>` | 查询发票详情 |
| `DELETE /invoices/<id>` | 删除发票记录 |
| `GET /invoices/export` | 导出发票记录 CSV |
| `GET /debug-doc` | 诊断 LibreOffice / 文档转换环境 |

当前前端主流程走的是异步接口 `/process/start` + `/process/<job_id>` 轮询。

### 3.3 核心处理层

`docflow_core.py` 中的 `DocFlowProcessor` 是统一入口。它注册了 5 类解析器：

- `PDFParser`
- `WordParser`
- `ExcelParser`
- `PPTXParser`
- `TextParser`

处理流程是：

1. 根据扩展名选择解析器
2. 解析正文、表格和元数据
3. 对文本结果生成关键词和摘要
4. 如果开启发票识别，则调用 `InvoiceExtractor`
5. 按 `txt/json/markdown/csv` 输出格式生成结果

### 3.4 OCR 与图片处理层

图片走 `app.py` 里的 `process_image_ocr(...)`，与普通文档解析是另一条链路。当前实现特点：

- OCR 引擎顺序可通过环境变量控制
- 代码支持 `RapidOCR`、`PaddleOCR`、`Tesseract`、`EasyOCR`
- 当前轻量云镜像默认安装的是 `RapidOCR + Tesseract`
- 支持图片 OCR 缓存
- 支持云环境下的自动降采样和线程限制

## 4. 当前已实现功能

### 4.1 文档解析

- 支持 `pdf/doc/docx/xls/xlsx/pptx/txt/md/json/csv`
- PDF 提供三种运行模式：高精度、平衡、快速
- 统一返回文本、表格、统计信息和格式化输出

### 4.2 OCR 能力

- 图片文件直接进入 OCR 流程
- PDF 在需要时会触发 OCR 增强
- OCR 失败会按引擎顺序回退，而不是单点失败

### 4.3 发票识别与记录

- 既支持在普通文档处理结果上追加发票识别
- 也支持图片 OCR 后直接提取发票字段
- 识别出的发票会写入 SQLite 数据库 `data/invoices.db`
- 支持在前端查看发票历史记录并导出 CSV

### 4.4 批量测试与模式实验

- 前端可直接发起“一键批测”
- 前端可对同一 PDF 依次运行 `accurate / balanced / fast`，再给出推荐模式
- 报告文件可以通过 `/reports/...` 直接访问

### 4.5 依赖检查

- 提供运行时依赖状态检查
- 能提示 OCR、LibreOffice、Python 包等缺失项
- 本地环境下可以尝试自动补装部分依赖

## 5. 关键主链路

### 5.1 通用文档处理链路

1. 前端上传文件到 `/process/start`
2. `app.py` 保存临时文件并创建后台线程
3. 非图片文件进入 `DocFlowProcessor.process(...)`
4. 解析结果经过 `augment_result_payload(...)` 补充统一元信息
5. 如果开启发票识别，结果中的 `statistics.invoice_fields` 会补齐
6. 如果识别为发票，会自动写入 SQLite
7. 前端通过 `/process/<job_id>` 轮询直到完成

### 5.2 图片 OCR / 发票链路

1. 图片文件进入 `process_image_ocr(...)`
2. 按配置顺序尝试 OCR 引擎
3. 生成文本、OCR 元信息和统计项
4. 如果开启发票识别，调用 `InvoiceExtractor.extract(...)`
5. 识别成功后写入 `invoice_db.py` 管理的 SQLite 表

## 6. 测试与评测方式

当前仓库不是传统的 `pytest` / `unittest` 结构，而是“样本 + 清单 + 报告”的数据驱动测试方式。

### 6.1 通用批量测试

脚本：`scripts/run_batch_tests.py`

用途：

- 运行 `sample_data/test_documents`
- 运行 `sample_data/test_documents_edge_cases`
- 统计成功率、预期匹配率、错误分类
- 生成 `report.md`、`summary.html`、`results.json`、`results.csv`

### 6.2 清单式评测

脚本：`scripts/run_evaluation_set.py`

用途：

- 基于 `sample_data/evaluation_set/sample_manifest.json`
- 更适合做固定样本集的规则校验和对比

### 6.3 发票专项评测

脚本：`scripts/run_invoice_evaluation.py`

配套清单：

- `发票样本/invoice_test_manifest.csv`
- `发票样本/invoice_excel_manifest.csv`

这部分的评测口径已经单独写在 `发票样本/评测说明.md` 中，当前做法是把：

- 发票/非发票判定
- 字段级命中率

分开统计，避免把没有字段真值的公开数据集误当成字段准确率实验。

### 6.4 报告输出目录

报告统一输出到 `reports/`，当前常见目录形态为：

- `reports/batch_test_<timestamp>/`
- `reports/evaluation_<timestamp>/`
- `reports/invoice_evaluation_<timestamp>/`

## 7. 当前部署形态

项目现在同时支持两种运行方式：

- 本地开发：直接 `python app.py`
- 轻量云部署：使用 `Dockerfile` + `render.yaml`

当前 Docker 方案使用：

- `gunicorn` 作为生产入口
- `RapidOCR + Tesseract` 作为默认 OCR 组合
- `requirements-cloud.txt` 作为轻量依赖集合

## 8. 当前限制与风险

- 长任务仍在 Web 进程创建的后台线程中执行，没有接入外部任务队列
- `uploads_temp/`、`reports/`、`data/invoices.db` 在容器中默认不是持久化存储
- 旧版 `.doc/.xls` 的兼容性仍依赖 LibreOffice 等外部工具
- 发票抽取当前是规则/启发式实现，不是训练型模型
- 没有多用户、鉴权、权限隔离和对象存储

## 9. 适合论文或答辩强调的点

如果这个仓库继续用于毕业设计写作，当前更适合强调下面这些“已落地”的工程点：

- 解析器抽象与多格式统一输出
- PDF 文本层 + OCR 混合解析与模式切换
- 多 OCR 引擎回退和云环境优化
- 发票字段抽取与 SQLite 持久化
- 基于样本集和清单的批量评测体系
- Docker 化轻量部署与在线演示
